# 009 — Порядок быстрых передач

Тип: поведение
Основание: FR-14
Зависимости: 006, 007, 008
Половины: backend — tasks-core + audit + socket-service; frontend. Четыре Change, четыре PR, принимаются вместе
Результат: при цепочке быстрых передач журнал и экраны показывают правильный порядок и итог

## Контракты
- contracts/events/task-transferred.audit.schema.json — порядковый номер передачи (не меняется)
- contracts/events/task-transferred.realtime.schema.json — порядковый номер передачи (не меняется)
- contracts/socket/task-transferred.message.json — порядковый номер передачи (не меняется)

## Общая приёмка (собранное приложение)
AC-009-1 Цепочка
  WHEN TASK-42 передали Анна → Борис, затем Борис → Вера в течение секунды
  THEN в журнале аудита две записи в этом порядке
   AND у Веры TASK-42 в «Моих задачах», исполнитель Вера
   AND у Анны и Бориса TASK-42 нет

## Backend-половина
AC-009-B1 Журнал
  WHEN события о передачах TASK-42 пришли в audit в обратном порядке
  THEN записи в журнале в порядке передач

AC-009-B2 Публикация
  WHEN передачи TASK-42 выполнены одна за другой
  THEN события по TASK-42 опубликованы в порядке передач, в том числе после сбоя доставки

AC-009-B3 Доставка клиентам
  WHEN socket-service получил события по TASK-42
  THEN клиентам они уходят в порядке передач

## Frontend-половина
AC-009-F1 Устаревшее сообщение
  WHEN клиент получил сообщение о передаче TASK-42 с номером меньше уже применённого
  THEN состояние не меняется
  Пример: применено «Борис → Вера», пришло «Анна → Борис» → у Веры TASK-42 остаётся,
  у Бориса не появляется

## Границы
Вне slice: одиночные передачи (006, 007, 008). Вариант «одной гарантии на стороне клиента
достаточно» отвергнут Dev Spec: порядок строгий и для журнала, и для экранов.
