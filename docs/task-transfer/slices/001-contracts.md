# 001 — Контракты

Тип: подготовка
Основание: все FR и NFR (форма данных, ошибки, события)
Зависимости: нет
Половины: tasks-core, socket-service, audit, frontend — у каждого сервиса свои контракты, PR в каждый репозиторий; ревьюят все стороны вместе
Результат: контракты передачи задачи лежат в коде своих владельцев, и все стороны могут работать независимо

## Контракты (создаются в этом slice)
Владелец контракта — сервис, который его отдаёт или публикует. Потребители ссылаются на версию владельца.

tasks-core:
- contracts/tasks-core.openapi.yaml — НОВОЕ: поиск получателя по задаче, передача задачи (получатель, причина), формат ответа и ошибок
- contracts/events/task-transferred.audit.schema.json — НОВОЕ: событие для журнала аудита (задача, кто передал, кому, когда, причина, порядковый номер передачи по задаче)
- contracts/events/task-transferred.realtime.schema.json — НОВОЕ: событие для realtime-доставки (задача, прежний и новый исполнитель, адресаты, порядковый номер передачи по задаче)
- application/ports/ProjectMembers.ts — НОВОЕ: порт к user-core (участники проекта, активность, роль, должность; ошибка «недоступно»)
- domain/errors/TaskTransferErrors.ts — НОВОЕ: NOT_ASSIGNEE, TASK_CLOSED, RECIPIENT_NOT_ELIGIBLE, SELF_TRANSFER, INVALID_REASON, MEMBERS_UNAVAILABLE; TASK_TRANSFERRED — отказ при сохранении задачи, которую передали (без данных о получателе)
- tests/fixtures/task-transfer.ts — НОВОЕ: данные ниже

socket-service:
- contracts/socket/task-transferred.message.json — НОВОЕ: сообщение, которое клиент получает по сокету (задача, прежний и новый исполнитель с именем, порядковый номер передачи)
- сообщение о закрытии задачи (существующее, используется в FR-10) — не меняется

audit:
- подписка на contracts/events/task-transferred.audit.schema.json из tasks-core — НОВОЕ: ссылка на версию контракта владельца, своих схем не вводит

frontend:
- типы клиента из tasks-core.openapi.yaml и task-transferred.message.json — НОВОЕ

## Общая приёмка
```
AC-001-1 Контракты согласованы
  WHEN PR с контрактами открыты во всех четырёх репозиториях
  THEN каждый одобрили представители frontend, tasks-core, audit и socket-service
   AND потребители ссылаются на те же версии контрактов, что опубликовали владельцы
```

## Backend-половина
```
AC-001-B1 Контракты валидны
  WHEN контракты и fixtures собраны
  THEN схемы событий, сообщения сокета и openapi проходят валидацию, fixtures соответствуют схемам
```

## Frontend-половина
```
AC-001-F1 Типы клиента
  WHEN клиент собран
  THEN типы ответа передачи, поиска и сообщения сокета выводятся из контрактов владельцев
```

## Границы
Вне slice: любое поведение. Реализация поиска (002), передачи (003, 004), доступа (005),
аудита (006), realtime (007, 008), порядка (009).
