# 001 — Контракты

Тип: подготовка
Основание: все FR и NFR (форма данных, ошибки, события)
Зависимости: нет
Половины: backend + frontend, PR ревьюят обе стороны вместе
Результат: контракты передачи задачи лежат в коде, и обе стороны могут работать независимо

## Контракты (создаются в этом slice)
- contracts/tasks-core.openapi.yaml — НОВОЕ: поиск получателя по задаче, передача задачи (получатель, причина), формат ответа и ошибок
- contracts/events/task-transferred.audit.schema.json — НОВОЕ: событие для журнала аудита (задача, кто передал, кому, когда, причина, порядковый номер передачи по задаче)
- contracts/events/task-transferred.realtime.schema.json — НОВОЕ: событие для realtime-доставки (задача, прежний и новый исполнитель, адресаты, порядковый номер передачи по задаче)
- contracts/socket/task-transferred.message.json — НОВОЕ: сообщение, которое клиент получает по сокету
- tasks-core: application/ports/ProjectMembers.ts — НОВОЕ: порт к user-core (участники проекта, активность, роль, должность; ошибка «недоступно»)
- tasks-core: domain/errors/TaskTransferErrors.ts — НОВОЕ: NOT_ASSIGNEE, TASK_CLOSED, RECIPIENT_NOT_ELIGIBLE, SELF_TRANSFER, INVALID_REASON, MEMBERS_UNAVAILABLE
- tests/fixtures/task-transfer.ts — НОВОЕ: данные ниже

Сообщение о закрытии задачи (существующее, используется в FR-10) — не меняется, ссылка добавляется в индекс контрактов.

## Общая приёмка
AC-001-1 Контракты согласованы
  WHEN PR с контрактами открыт
  THEN его одобрили представители frontend, tasks-core, audit и socket-service

## Backend-половина
AC-001-B1 Контракты валидны
  WHEN контракты и fixtures собраны
  THEN схемы событий и openapi проходят валидацию, fixtures соответствуют схемам

## Frontend-половина
AC-001-F1 Типы клиента
  WHEN клиент собран
  THEN типы ответа передачи, поиска и сообщения сокета выводятся из контрактов

## Границы
Вне slice: любое поведение. Реализация поиска (002), передачи (003, 004), доступа (005),
аудита (006), realtime (007, 008), порядка (009).
