# Передача задачи другому пользователю — Dev Spec

## Цель
Исполнитель может передать свою задачу другому участнику проекта с указанием причины,
чтобы работа не стояла, когда он не может или не должен её вести. До этой фичи сменить
исполнителя было нельзя.

## Данные для примеров
Проект «Мобильное приложение»:
- Анна Петрова, разработчик (активна)
- Борис Иванов, разработчик (активен)
- Вера Смирнова, руководитель проекта (активна)
- Глеб Орлов, разработчик (заблокирован)
- Дина Козлова, разработчик, участник другого проекта

Задача TASK-42 «Починить вход по SMS», статус «В работе», исполнитель Анна.
Задача TASK-50 «Обновить иконки», статус «Закрыта», исполнитель Анна.

## Функциональные требования

FR-1  Передать задачу может только её текущий исполнитель.
      Пример: Анна в карточке TASK-42 видит «Передать». Вера открывает TASK-42 и
      кнопки не видит. Если запрос от Веры всё же пришёл, отказ:
      «Передать задачу может только исполнитель».

FR-2  Получатель выбирается поиском по ФИО среди активных участников проекта.
      Совпадение ищется по подстроке в любой части ФИО, без учёта регистра.
      Подсказки появляются с 2 символов, показываются 20 наиболее подходящих:
      сначала совпадения с начала слова (имени, фамилии или отчества), затем
      совпадения внутри слова; внутри каждой группы — по алфавиту ФИО.
      В подсказке видны имя и должность, других данных нет.
      Подсказки обновляются через 200 мс после последнего ввода.
      Искать кандидатов может любой, кто видит задачу (исполнитель и руководитель).
      Если поиск не удался, показывается «Что-то пошло не так».
      Пример: «Б» → подсказок нет. «Бор» → «Борис Иванов, разработчик».
      «Ива» → Борис Иванов. «ова» → Анна Петрова, Вера Смирнова
      (Дина Козлова — нет, другой проект).
      «ан» и «Ан» дают одинаковый результат.
      «Ан» при 35 подходящих участниках → 20 подсказок, совпадения с начала слова
      впереди: Анна Петрова выше Бориса Иванова.
      «Гле» → пусто (заблокирован). «Дин» → пусто (не участник проекта).
      Сам пользователь в подсказках есть.

FR-3  Причина передачи обязательна, не длиннее 2048 символов. Пустая причина,
      причина из одних пробелов или длиннее 2048 символов не принимается.
      Пример: Анна выбрала Бориса, причину не заполнила → передать нельзя.
      Причина из 2048 символов принимается, из 2049 — нет.

FR-4  Передача выполняется сразу, согласие получателя не нужно. Статус задачи
      не меняется.
      Пример: Анна передаёт TASK-42 Борису с причиной «Ухожу в отпуск» →
      исполнитель Борис, статус «В работе».

FR-5  Задачу в статусе «Закрыта» передать нельзя: кнопки «Передать» в ней нет.
      Остальные статусы, включая «Отменена», передаче не мешают.
      Пример: Анна открывает TASK-50 → кнопки «Передать» нет. Если запрос всё же
      пришёл → отказ «Задача закрыта».

FR-6  Задачу видят только её исполнитель и руководитель проекта. После передачи
      прежний исполнитель теряет к ней доступ: задача пропадает из его «Моих задач»,
      по ссылке открыть её нельзя.
      Пример: после FR-4 Анна открывает ссылку на TASK-42 → «Нет доступа к задаче».
      Вера видит TASK-42 с исполнителем Борисом.

FR-7  При отказе пользователь видит причину:
      - «Вы больше не исполнитель задачи» (в том числе при повторе уже выполненной
        передачи);
      - «Задача закрыта»;
      - «Этому пользователю нельзя передать задачу» (не участник проекта или неактивен);
      - «Нельзя передать задачу самому себе»;
      - «Передача временно невозможна, попробуйте позже» (данные об участниках
        проекта недоступны).
      При первых двух отказах карточка закрывается и пользователь попадает в
      «Мои задачи» с текстом отказа. При остальных диалог остаётся открытым
      с введёнными данными.
      Пример: Анна дважды нажимает «Передать» Борису. Первый запрос успешен,
      второй получает «Вы больше не исполнитель задачи». Так задумано.
      Пример: Анна выбирает себя → «Нельзя передать задачу самому себе».

FR-8  Пока передача не подтверждена, показывается ожидание и повторно отправить
      передачу нельзя. Результат появляется только после ответа. После успеха пользователь переходит в «Мои задачи» и видит
      сообщение о передаче.
      Пример: «Задача TASK-42 передана: Борис Иванов».

FR-9  После передачи изменения видны без перезагрузки:
      - у нового исполнителя задача появляется в «Моих задачах»;
      - у руководителя в задаче меняется исполнитель;
      - у прежнего исполнителя на других вкладках и устройствах задача пропадает
        из списка, открытая карточка закрывается с сообщением о передаче,
        несохранённые правки теряются.
      Пример: у Анны на ноутбуке открыта TASK-42 с недописанным комментарием.
      Анна передаёт задачу с телефона → на ноутбуке карточка закрывается,
      сообщение «Задача TASK-42 передана: Борис Иванов».

FR-10 Если задачу закрыли, пока у исполнителя открыт диалог передачи, карточка
      вместе с диалогом исчезает без перезагрузки.
      Пример: Анна открыла диалог по TASK-42, Вера закрыла задачу → у Анны
      карточка и диалог исчезли.

FR-11 Прежний исполнитель не может сохранить изменения задачи после передачи.
      Его клиент ведёт себя так же, как при получении передачи по FR-9.
      Пример: уведомление о передаче до ноутбука Анны ещё не дошло, Анна нажимает
      «Сохранить» → отказ, карточка закрывается, сообщение о передаче.

FR-12 Пользователь, который был не в сети в момент передачи, при входе видит
      актуальное состояние. Пропущенные уведомления о передачах не показываются.
      Пример: Борис был офлайн. При входе TASK-42 есть в его «Моих задачах»,
      отдельного уведомления нет.

FR-13 Каждая передача попадает в журнал аудита: кто передал, кому, когда, причина.
      Журнал видят только администраторы, в существующем интерфейсе аудита.
      Запись может появиться с задержкой, но не теряется. Временный сбой доставки
      не отменяет передачу.
      Пример: запись «Анна Петрова → Борис Иванов, TASK-42, 26.10.2026 14:05,
      «Ухожу в отпуск»».

FR-14 Порядок передач одной задачи сохраняется: в журнале аудита записи идут
      в порядке передач, на экранах итог соответствует последней передаче.
      Устаревшее уведомление не перетирает более новое.
      Пример: TASK-42 передали Анна → Борис → Вера за секунду. В журнале две записи
      в этом порядке, у руководителя исполнитель Вера, у Бориса задачи нет.

## Нефункциональные требования

NFR-1 Передача задачи: p95 ≤ 300 мс в проекте до 500 участников.
NFR-2 Поиск получателя: p95 ≤ 300 мс в проекте до 500 участников.
NFR-3 Журнал аудита: 0 потерянных записей о передачах, в том числе при временной
      недоступности доставки.
NFR-4 Запись о передаче появляется в журнале аудита: p95 ≤ 1 с с момента передачи
      (без учёта периодов недоступности доставки, см. NFR-3).

## Вне scope
- Передача задачи руководителем или администратором, в том числе задач уволенных
  и заблокированных сотрудников (отдельная фича).
- Массовая передача нескольких задач.
- Email и push-уведомления.
- Согласие получателя (принять или отклонить).
- Наблюдатели, соисполнители, подзадачи.
- Показ загрузки получателя в поиске.
- История передач в карточке задачи.
- Доставка пропущенных уведомлений пользователю, который был офлайн.
- Скрытие самого пользователя из поиска (упрощение, может вернуться).
- Время появления изменений на экранах других пользователей не нормируется
  (зависит от сети пользователя).
