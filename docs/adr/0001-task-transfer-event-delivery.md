# ADR-0001: Гарантированная и упорядоченная доставка событий о передаче задачи

Статус: принято, 26.10.2026
Фича: [Передача задачи](../task-transfer/spec.md)
Затрагивает slices: 006, 007, 009

## Контекст

Dev Spec требует от событий о передаче:
- FR-13, NFR-3 — запись в журнале аудита не теряется, в том числе при временной недоступности доставки; временный сбой не отменяет передачу;
- FR-13 — одна передача — одна запись, повторная доставка не даёт дубля;
- NFR-4 — p95 ≤ 1 с от передачи до записи в журнале;
- FR-14 — порядок передач одной задачи строгий: в журнале и на экранах; устаревшее не перетирает новое;
- FR-9, FR-12 — realtime-доставка, пропущенное офлайн не досылается.

Уже решено в brainstorming: tasks-core публикует в Kafka два отдельных события — для audit
и для socket-service. БД tasks-core — PostgreSQL. socket-service работает в одном инстансе. У каждого сервиса свои контракты, владелец события — tasks-core (001).

Проблема: сохранить передачу в БД tasks-core и опубликовать событие в брокер — две разные
операции. Если сделать их по очереди, падение между ними даёт либо передачу без события
(нарушение NFR-3), либо событие без передачи.

## Варианты

### A. Публиковать после коммита (dual write)
Сохранили передачу, затем отправили события.
- плюс: проще всего, ничего нового в инфраструктуре;
- минус: падение процесса или недоступность брокера после коммита теряет событие — NFR-3 не выполняется;
- минус: ретраи в памяти процесса не переживают рестарт.

Отклонён: не выполняет NFR-3 и FR-13.

### B. Transactional outbox в tasks-core
В одной транзакции с передачей в таблицу outbox пишутся оба события. Отдельный relay
читает outbox и публикует в брокер, отмечая отправленное.
- плюс: событие есть тогда и только тогда, когда есть передача;
- плюс: брокер недоступен → события копятся в outbox и уходят после восстановления (FR-13);
- плюс: relay публикует в порядке записи, что даёт основу для FR-14;
- минус: доставка at-least-once — потребители обязаны отбрасывать повторы;
- минус: задержка = интервал опроса relay; для NFR-4 он должен быть заметно меньше 1 с.

### C. CDC (чтение журнала изменений БД, например Debezium)
Как B, но вместо relay события снимаются из журнала изменений БД.
- плюс: нет опроса, малая задержка;
- минус: новая инфраструктура и эксплуатация ради одной фичи.

Отложен: имеет смысл, если CDC уже есть в компании.

## Решение

Вариант B — transactional outbox в PostgreSQL tasks-core, плюс порядковый номер передачи по задаче.

1. **Номер передачи.** У задачи есть монотонный счётчик передач `transferSeq`. Передача увеличивает
   его в той же транзакции. Номер попадает в оба события и в сообщение сокета (контракты 001 уже
   содержат «порядковый номер передачи по задаче»).
2. **Outbox.** В транзакции передачи пишутся две записи outbox: событие для audit и для socket-service.
   Каждое событие получает уникальный идентификатор.
3. **Relay.** Публикует записи outbox в Kafka в порядке создания. Ключ сообщения — идентификатор
   задачи: события одной задачи попадают в одну партицию и читаются в порядке публикации.
   Relay отправляет записи одной задачи последовательно, не начиная следующую до подтверждения
   предыдущей, иначе ретрай может переставить их.
4. **audit.** Запись идемпотентна по паре (задача, `transferSeq`): повтор не создаёт дубль (AC-006-B6).
   Журнал по задаче упорядочен по `transferSeq`, а не по времени прихода (AC-009-B1).
5. **socket-service.** Один инстанс читает партиции по порядку и пересылает сообщение адресатам
   с `transferSeq`, без хранения пропущенного (FR-12).
6. **Клиент.** Хранит последний применённый `transferSeq` по задаче и игнорирует сообщения с меньшим
   или равным номером (AC-009-F1). При одном инстансе socket-service это защита от
   переподключений и ретраев, а не от обгона между инстансами.
7. **Ответ пользователю** не ждёт публикации: передача успешна после коммита транзакции (FR-13).

## Последствия

- Slice 006 вводит outbox и relay. Slice 007 добавляет второе событие в ту же транзакцию.
  Тот, кто стартует первым, вводит механизм, второй использует его (конфликт 006/007 снят).
- Slice 009 не исчезает, но уменьшается: порядок публикации даёт relay с ключом по задаче
  (AC-009-B2, B3 закрываются тестами без нового кода), а упорядочивание журнала по номеру (B1)
  и отбрасывание устаревшего на клиенте (F1) остаются отдельной работой.
- Потребители обязаны быть идемпотентными; это правило стоит записать в AGENTS.md audit
  и socket-service.
- Таблица outbox растёт: нужна очистка отправленных записей (срок — вопрос ниже).
- NFR-4 зависит от интервала опроса relay и лага брокера; проверяется AC-006-B5.

## Не выяснено (не блокирует старт 006 и 007)

- Есть ли в компании готовый outbox или CDC. Если найдётся — переиспользовать вместо нового relay;
  решение B от этого не меняется.
- Срок хранения отправленных записей outbox. Решается в Change slice 006; до решения записи
  не удаляются.
- Если socket-service станет масштабироваться на несколько инстансов, вернуться к этому ADR:
  порядок для одного пользователя тогда держит только клиентская проверка `transferSeq`.
