## Что агент нашёл в коде

> Кода сервисов в демо нет. Ниже — предполагаемое состояние tasks-core после 001 и 002,
> как если бы агент его прочитал.

- Контракт `POST /tasks/{id}/transfer` и ошибки `NOT_ASSIGNEE`, `INVALID_REASON` уже есть (001),
  реализации нет — контроллер отвечает 501.
- Задача сохраняется через `TaskRepository.save()` без проверки версии. Две одновременные передачи
  одной задачи из двух вкладок обе прочитают «исполнитель — Анна» и обе пройдут.
  → техническое решение: условное обновление «исполнитель всё ещё Анна», проигравший получает `NOT_ASSIGNEE`.
  Поведение уже есть в Dev Spec (FR-7), новое правило не нужно.
- В таблице задач нет счётчика передач, а ADR-0001 требует `transferSeq`, который увеличивается
  в транзакции передачи. 006, 007 и 009 будут на него опираться.
  → техническая задача: добавить поле в этом Change, публикацию событий не трогать (006, 007).
- Валидация строк в домене обрезает пробелы по краям (`trim`) у названия задачи перед сохранением.
  Для причины Dev Spec говорит только «из одних пробелов не принимается» и «не длиннее 2048».
  → **продуктовый вопрос**, см. ниже.
- Проверки получателя (участник проекта, активен, не сам исполнитель) — это slice 004. Если 003
  выкатится раньше 004, сервер примет передачу Глебу или Дине.
  → в описание PR и в slices/README.md: 003 и 004 включаются вместе (см. «Что забираем»).

## JIT-вопрос (агент остановился)

Пробелы в начале и в конце причины: сохраняем причину как ввели или обрезаем?

Пример: причина «␣␣Ухожу в отпуск␣» — что попадёт в журнал аудита и в тост?
